1. Executive Summary

VendoPOS is a multi-tenant Software-as-a-Service platform that combines a cloud Point of Sale with a full Enterprise Resource Planning back office. One platform operator (the Super Admin) sells subscriptions to many independent businesses (Merchants). Every Merchant runs on its own isolated Tenant: its products, sales, staff, customers and finances are fenced off from every other store.

The platform is designed from the ground up for the Philippine market: prices are in Philippine peso (₱), VAT is the 12% price-inclusive BIR model, invoices carry gap-free BIR-style serial numbers, receipts carry machine-accreditation fields (PTU, MIN, serial), e-wallet rails GCash, Maya and QR Ph are first-class payment methods, and payroll applies Philippine overtime and night-differential norms in Manila time.

What the system does

Front of house

  • Touch POS terminal with cart, discounts, loyalty redemption and split tender channels
  • Barcode scan-to-cart (keyboard-wedge scanners)
  • Scan-to-pay QR for GCash / Maya / QR Ph
  • Customer-facing second display
  • HTML and ESC/POS thermal receipts (USB & Bluetooth)
  • Shared-terminal cashier PIN switching, shift X-Read / Z-Read

Back office (ERP)

  • Inventory with an immutable stock-movement ledger
  • Procurement: suppliers, purchase orders, receiving, reorder suggestions
  • Manufacturing: recipes / bill of materials and production runs
  • Finance: expenses, P&L, Balance Sheet, Cash Flow
  • HR: employees, attendance, timecards, gross→net payroll with SSS / PhilHealth / Pag-IBIG / withholding tax, CSV export
  • CRM: customers and loyalty points

Compliance & control

  • Serialized invoices per tenant (SI-000123), locked under concurrency
  • Per-product VAT class (VATable / Exempt / Zero-rated) on receipts and the BIR ledger
  • Monthly BIR sales ledger (JSON + CSV)
  • Voids/returns as contra-entries; POS audit log of sensitive actions
  • Cash-drawer variance flags to the centavo
  • Every refund and void needs a reason, reviewed by the owner

Platform operations

  • Lead pipeline with e-mail verification and atomic lead → tenant provisioning
  • Self-serve sign-up with a 14-day trial
  • MRR / ARPA billing analytics, subscriber register
  • Live system-health stream (SSE), cross-tenant compliance register
  • Support impersonation of a merchant owner
  • At-risk store watchlist, platform broadcasts and an admin audit trail

Key engineering principles

  • Money is integer centavos end-to-end. No floating-point peso arithmetic is persisted; VAT is computed once at checkout and frozen.
  • Tenant scope comes from the session, never the request body. Every query is threaded with the tenant id taken from the signed session cookie.
  • ACID by default. Checkout, voids/returns, receiving, production, payroll and provisioning are each single all-or-nothing transactions.
  • Server is the source of truth for prices. The terminal only sends product ids and quantities; the server re-derives every price.
  • Pure, IO-free calculation cores (payroll, financial reports, reorder, forecast, theme) are unit-tested in isolation.
  • Manila time (UTC+8) defines "today", monthly buckets and payroll days so figures line up with the local retail day.

Request pipeline

  1. CSRF guard (csrfOriginGuard, mounted first): every POST / PUT / PATCH / DELETE must carry an Origin (or Referer) inside the CORS allow-list, otherwise 403.
  2. helmet sets security headers; CORS allows the configured origins with credentials: true and the verbs GET, POST, PUT, PATCH, DELETE, OPTIONS.
  3. JSON bodies are capped at 100 kB; cookies are parsed for the session JWT.
  4. Public seams mount first: /health, /uploads (served from the media_objects table, with a sandboxing CSP), /auth, /api/v1/public, /api/leads.
  5. Trial checkpoint (enforceTrialStatus) fences a lapsed-trial store out of every authenticated merchant module with 402 and a recovery marker. It is a no-op for anonymous and Super Admin requests.
  6. Each module router applies requireRole(...) and, where premium, requireFeature(...).
  7. Rate limiting (express-rate-limit) throttles brute force on login, PIN, sign-up and forgot-PIN (10 failed attempts per 15 minutes per IP) and floods on lead forms (30 per hour per IP), answering 429.
  8. Unknown routes return 404 {"ok":false,"error":"Not found"}; a central error handler returns a generic 500 and never leaks stack traces.

Same-origin API proxy

The website and the API live on different hosts (Vercel and Render). To keep the session cookie first-party — browsers increasingly refuse cross-site cookies — frontend/next.config.ts rewrites /api/*, /auth/* and /uploads/* on vendopos.shop to the backend (API_PROXY_TARGET, default https://api.vendopos.shop). The browser therefore only ever talks to vendopos.shop. Consequence: no frontend page may live under /api, /auth or /uploads (the sign-up page is /signup).

6. Tenant Lifecycle & Trials

Each tenant row carries status ∈ {trial, active, trial_expired, suspended} plus trial_starts_at / trial_ends_at.

Two onboarding paths

Path A — self-serve sign-up

POST /auth/signup from the /signup page (linked from pricing) creates a fresh, isolated tenant on the chosen plan, opened on a 14-day trial, with the owner account and an onboarding e-mail.

Path B — sales-led (Lead)

The demo form writes a Lead (PENDING_DEMO) and e-mails the prospect a verification link; the admin pipeline shows a verified / unverified badge. The Super Admin approves it, which atomically inserts the tenant, inserts the owner as MERCHANT_OWNER and flips the lead to APPROVED. Slug or owner-email collisions roll back with 409.

Lazy trial expiry (no cron)

  1. On any request after trial_ends_at, evaluateTenantStatus runs a single guarded UPDATE … WHERE status='trial' AND trial_ends_at <= now().
  2. Only the request that wins the flip sends the trial-expired recovery e-mail — so it is sent exactly once, even under concurrency.
  3. The trial middleware then returns 402 for merchant modules; /auth/me reports the lapsed state so the workspace swaps to the Trial Recovery view.
  4. Sign-in, /auth/me and the marketing site stay reachable so the owner can upgrade and recover.

Lifecycle is resolved live from the database, never from the JWT, so an upgrade or lapse takes effect on the very next request. The Super Admin can change a tenant's plan or status via PATCH /api/v1/admin/tenants/:id.

7. Authentication, Roles & Sessions

Sign-in methods

MethodFlow
Google OAuthGET /auth/google mints a CSRF state — a signed (HMAC with the JWT secret), timestamped token carried in the URL, so it needs no cookie and survives the proxy — and redirects to Google. /auth/google/callback verifies state, exchanges the code, looks up the e-mail in users, signs the JWT, sets the cookie and redirects to the role's dashboard. Unknown e-mails get ?error=not_provisioned.
Owner / manager passwordPOST /auth/password-login with Store ID + e-mail + password. Owners set or change a password via /auth/password; status via /auth/password/status. A first-login onboarding card prompts owners to set one.
Cashier PINPOST /auth/store resolves the Store ID (tenant slug); POST /auth/pin verifies a 4-digit PIN within that tenant (optionally pinned to a selected userId) and swaps the cookie. On a warm terminal the active session's tenant always wins, so a typed Store ID can never reach across tenants.

Forgot-PIN workflow

Cashiers never set their own PIN. POST /auth/cashiers lists a store's cashier names; POST /auth/pin/forgot raises one pending reset request per cashier (partial unique index, idempotent). The owner resolves it in Cashiers by setting a new PIN (resolves the request in the same transaction) or rejecting it.

Sessions & security

  • JWT in an HTTP-only cookie (vendopos_session), 7-day lifetime. Served first-party through the same-origin proxy; SameSite is derived from the frontend URL scheme (HTTPS → None + Secure, HTTP → Lax) and can be forced with COOKIE_SAMESITE.
  • In production the API refuses to boot without a JWT_SECRET of at least 32 characters.
  • Login, PIN, sign-up and forgot-PIN are rate-limited (10 failed attempts / 15 min / IP).
  • Each sign-in creates a row in sessions (revocable device sessions) and login_events (login audit). Users can revoke a single session or all others.
  • PINs hashed as scrypt$salt$hash; passwords as pw1$salt$hash (scrypt, per-user salt); verification is constant-time (timingSafeEqual).
  • GET /auth/me returns {userId, tenantId, role, email, name, tenantName, …} with the tenant name, tier, status and theme looked up live.
  • Impersonation: POST /auth/impersonate (Super Admin) mints an owner session for support, shown with an Impersonation Banner; /auth/impersonate/stop returns to /admin/tenants.
  • Password policy (shared backend + client): 10–128 characters, character variety required, common passwords rejected, blank or space-padded passwords rejected. Applied to sign-up, password change, first-run onboarding and the lead owner password.
  • POST /auth/logout clears the cookie. All sign-out and terminal-lock actions go through a confirm dialog.

8. Point of Sale (POS) Terminal

Route /pos. Available to CASHIER, MANAGER and MERCHANT_OWNER. On a fresh device an Activation Wizard binds the terminal to a store.

Terminal features

  • Live catalog (GET /api/v1/pos/catalog): store name, categories and active products with price, stock, low-stock threshold and image; category filter and search.
  • Search or scan barcode: an Enter-terminated burst resolves to an exact SKU (then a sole-result fallback), drops it in the cart and clears for the next scan; transient "not found / out of stock" feedback. A global keyboard-wedge hook distinguishes scanner bursts from human typing by inter-key timing.
  • Cart: quantity edits, line voids (logged), cart-level discount (percent 0–100 or fixed amount) with label.
  • Customer attach & loyalty: search CRM customers, show balance, redeem points.
  • Payment: Cash (tendered and change), GCash, Maya, QR Ph (reference code). E-wallet rails show the merchant's uploaded scan-to-pay QR on the pad and the customer display.
  • Receipts: printable HTML receipt and direct ESC/POS thermal printing; reprint from sales history.
  • Sales history & returns modal: list sales, view details, void or return lines.
  • Shift controls: open shift with float, X-Read, close (Z-Read), open-drawer (logged).
  • Cashier switch: PIN pad with profile selector for shared terminals; terminal lock. If a store has no cashiers yet, the picker shows "No cashiers set up yet" and routes the owner to sign in and add them.
  • Labor clock: cashiers are clocked in automatically when they log in; End shift also clocks them out (owners and managers keep manual clock controls). A live shift-clock pill ticks in the header.
  • Theming: the tenant theme and announcement bar apply to the terminal.

Customer-Facing Display

Route /pos/customer-display: a clean, high-contrast second screen mirroring the live cart, discounts and totals. Sync is purely client-side over a same-origin BroadcastChannel (no server round-trip), so it is isolated to the active terminal browser. Selecting an e-wallet rail animates a QR presentation sheet open on the customer screen.

9. Checkout Engine, VAT & Invoicing

POST /api/v1/pos/orders is a single ACID transaction.

Request

{
  "items": [{ "productId": "uuid", "qty": 2 }],
  "paymentMethod": "Cash" | "GCash" | "Maya" | "QRPH",
  "tenderedCents": 50000,            // cash only
  "referenceCode": "GC-123…",        // e-wallet reference
  "discount": { "type": "percent" | "fixed", "value": 10, "label": "Senior" },
  "customerId": "uuid",              // optional CRM link
  "redeemPoints": 50                 // optional loyalty redemption
}

Steps inside the transaction

  1. Lock each product row SELECT … FOR UPDATE; re-derive prices from the DB (client prices are ignored).
  2. Abort with 400 (+ productId, available) if any line lacks stock.
  3. Apply the cart discount server-side (percent 0–100 or fixed centavos).
  4. Redeem loyalty: 1 point = ₱1, clamped to the live balance and to what remains payable.
  5. Compute VAT per VAT class with the shared computeVatBreakdown(): discounts are allocated pro-rata across classes, and VAT is extracted only from the VATable portion (vat = round(vatable × 12 / 112), 12% price-inclusive). Exempt and Zero-rated lines carry no VAT.
  6. Earn loyalty on what was actually paid: 1 point per ₱100 of net.
  7. Lock the per-tenant invoice_counters row and assign a gap-free, chronological reference SI-000123 (unique index backstop).
  8. Decrement stock through the stock ledger (reason='sale'), stamp the open shift_id, write the sales header and sale_items snapshots.
  9. After commit, raise low-stock notifications and push SSE low-stock events for any product that crossed its threshold.

10. Voids, Returns & POS Audit Log

Contra-entry model

A void or return never edits or deletes the original sale. It writes a new sales row with kind='void' or kind='return', negative quantities in sale_items (linked by reverses_sale_item_id) and a link reverses_sale_id. Every revenue total therefore nets automatically. The original's status moves to voided, partially_returned or returned. Reversal documents carry their own serial from reversal_counters.

  • GET /api/v1/pos/sales/:id shows per-line returnable quantity (sold − already returned).
  • POST /api/v1/pos/sales/:id/void reverses the whole sale; POST …/returns reverses chosen lines and quantities. A reason is mandatory for every void and return.
  • Stock is restored through the ledger (sale_void / return); loyalty points earned are clawed back and redeemed points restored proportionally.

POS audit log

Sensitive till actions are recorded in pos_audit_logs via POST /api/v1/pos/audit: void_item (line removed before payment), cancel_transaction (cart abandoned) and open_drawer (no-sale drawer open). Each row snapshots the cashier name, item, quantity, peso value and detail. Owners review it in Audit log (/dashboard/audit).

Refunds & voids review

GET /api/v1/pos/reversals (owner / manager only) lists every committed void and return with cashier, reason and amount. It appears as Refunds & voids on the Audit log page.

11. Cashier Shifts (X-Read / Z-Read)

The drawer ledger is keyed to the operator: one open shift per cashier per tenant (partial unique index). Sales are stamped with their shift_id, so tallies derive from real transactions.

EndpointBehaviour
POST /api/v1/pos/shifts/openOpens a shift with the opening cash float (openingCents; a per-cashier default float can be configured). 409 if one is already open.
GET /api/v1/pos/shifts/activeX-Read: live tallies — cash, e-wallet and card revenue, transaction count, and expected drawer cash = opening float + cash sales.
POST /api/v1/pos/shifts/closeZ-Read: locks the shift, snapshots per-channel rollups, computes variance to the centavo (counted − expected; + overage / − shortage), freezes an immutable audit snapshot. Body {countedCents, note?}.
POST /api/v1/staff/cashiers/:id/close-shiftOwner force-closes a cashier's forgotten shift.

An un-reconciled variance raises a security flag: a notification to the owner (if notify_variance is on) and an alert event on the Super Admin health stream. HR's Shift Discrepancy Matrix lists reconciliations (/api/v1/hr/shift-reconciliations).

12. Inventory & Stock Ledger

Catalog

  • Products: name, SKU (unique per tenant), price (pesos in, stored as centavos), stock, low-stock threshold, category, VAT class (VATable / Exempt / Zero-rated), active flag, optional image (≤ 2 MB, image/*). Derived lowStock flag.
  • Categories: nested via self-referential parent_id; unique name per tenant. Deleting a category makes its products uncategorised.
  • UI: Inventory Matrix, product form with image picker, category manager.

13. Procurement & Supply Chain Business

  • Suppliers: name, contact person, e-mail, phone, address, note, active flag — CRUD at /api/v1/procurement/suppliers.
  • Purchase orders: per-tenant serial reference (po_counters), supplier, line items (product, qty, unit cost), total, status draft → ordered → received or cancelled.
  • Receiving (POST /purchase-orders/:id/receive) restocks every line in one transaction via the ledger (po_receive) and records the unit cost used for inventory valuation.
  • Reorder suggestions (GET /reorder-suggestions): low-stock or depleted active products, a suggested quantity (pure suggestReorderQty) and the last known purchase cost (single-scan DISTINCT ON query, indexed).
  • Reorder modal: tick items, adjust quantities and create one draft PO in a click.
  • Summary KPIs at /summary; PO detail drawer in the UI.

14. Manufacturing (Bill of Materials) Enterprise

  • Recipes: an output product, output quantity per batch and components (raw-material products and quantity consumed per batch).
  • Produce (POST /recipes/:id/produce with batches): in one transaction, checks component availability, consumes components (produce_consume), adds output (produce_output), and writes a serialized production_runs record with its item breakdown.
  • Production history at /runs; summary KPIs at /summary.
  • Typical use: a café turning beans, milk and syrup into finished drinks or packaged goods.

Owner's equityAssets − Liabilities (residual) → Assets ≡ Liabilities + Equity by construction

Cash Flow — GET /finance/cash-flow?month=YYYY-MM

Direct method for one Manila month: opening cash (cumulative strictly before the month), inflows (sales collections), outflows (expenses + inventory received), net change, closing cash. Invariants: Opening + Net = Closing and Inflows − Outflows = Net.

Reports only sum pre-rounded integer centavos and never multiply by a tax rate, so they cannot introduce rounding drift. Builders live in the pure, unit-tested finance.reports.ts.

28. Security Model

  • Tenant isolation: tenant id comes only from the signed session and is threaded into every query; cross-tenant ids resolve as not found.
  • Defence in depth: role guard → tier guard → trial checkpoint → zod validation → parameterised SQL (no string-built queries) → DB check constraints.
  • Credentials: scrypt-hashed PINs and passwords with per-secret salts; constant-time comparison; PIN hashes never leave the DB.
  • Sessions: first-party HTTP-only cookie via the same-origin proxy, signed stateless CSRF state on OAuth, revocable sessions, login audit, 7-day expiry.
  • Abuse protection: per-IP rate limits on credentials and public forms; lead e-mail verification; the lead list is Super Admin only.
  • Fail-safe configuration: production requires a ≥ 32-character JWT_SECRET; a central error handler never exposes internals; dependencies patched for known Express and Next.js advisories.
  • CSRF: Origin-based guard on every state-changing request (needs no client token).
  • Clickjacking: the web app sends X-Frame-Options: SAMEORIGIN, CSP frame-ancestors 'self', X-Content-Type-Options: nosniff and a referrer policy.
  • Uploads: served with a sandbox CSP so a stored SVG can never run script.
  • Transport: helmet headers, explicit CORS allow-list with credentials, 100 kB JSON cap, 2 MB image cap with MIME filter.
  • Integrity: immutable stock ledger, contra-entry reversals, locked serial counters, frozen Z-Read snapshots, POS audit log.
  • Infrastructure: managed NeonDB (encryption at rest, backups) with the database TLS certificate verified (rejectUnauthorized: true), and HTTPS hosting.
  • Dependencies: npm audit --omit=dev is clean for backend and frontend; remaining advisories are in dev/test tooling only.
  • Security audit (6 Oct 2026, docs/security-audit-2026-10-06.md): DB TLS verification (medium), CSRF on body-less POSTs and clickjacking (low) fixed; legacy disk-upload sandbox needs staging validation; session revocation fails open during a DB outage (informational, accepted).
